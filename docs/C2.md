# CLAUDE.md — VetClinic API

## Projeto
API REST FastAPI (Python 3.12), monolito single-file. Gestão de clínica veterinária: tutores, pets, veterinários, produtos, agendamentos, atendimentos, faturas. Contrato formal em `SPEC.md` (fonte de verdade; qualquer alteração de comportamento deve manter `SPEC.md` e a suíte de aceitação satisfeitos).

## Arquivos
- `main.py` — **único arquivo de código**. Schema DB, modelos Pydantic, todas as rotas, toda a lógica de negócio. Qualquer mudança de funcionalidade é feita aqui.
- `SPEC.md` — contrato imutável (rotas, regras, status codes). **NÃO ALTERAR.** Consultar antes de mudar regra de negócio.
- `run.sh` — sobe `uvicorn main:app`, porta `$PORT` (padrão 8000), banco `$DB_PATH`. **NÃO ALTERAR.**
- `test.sh` — sobe servidor com banco temporário e roda pytest. **NÃO ALTERAR.**
- `requirements.txt` — deps travadas (fastapi 0.115.6, pydantic 2.10.4, uvicorn 0.34.0, httpx 0.28.1, pytest 8.3.4). **NÃO ALTERAR**; não adicionar libs fora desta lista.
- `tests/acceptance/*.py` — suíte de aceitação via HTTP (não importa `main`). **NÃO ALTERAR.** `conftest.py` tem fixtures (`api`, `novo_tutor`, `novo_pet`, `novo_vet`, `novo_produto`, `agendar`); `aceite_util.py` tem `BASE_URL`/`ok()`.

## Mapa de símbolos em `main.py` (por linha, pode mudar com edições — usar como índice)
- `db` (L7) — conexão sqlite3 global, `row_factory=Row`, `check_same_thread=False`.
- Schema (L9-17): tabelas `tutores, pets, veterinarios, produtos, agendamentos, atendimentos, faturas`. Ver "Esquema do banco" abaixo.
- `app` (L18) — instância FastAPI exportada, obrigatória pelo `run.sh`.
- `DT` (L19) = `"%Y-%m-%dT%H:%M"`; `CONSULTA` (L20) = `15000` (valor fixo da consulta em centavos).
- `err(code, msg)` (L23) — atalho para `raise HTTPException`.
- `get(table, id)` (L27) — SELECT por id ou 404. **Usado em toda rota que precisa validar existência.**
- `insert(table, data)` (L32) — INSERT genérico + commit + retorna row.
- `update(table, id, data)` (L38) — valida existência (404), UPDATE genérico + commit + retorna row.
- `parse(fmt)` (L45) — fábrica de `AfterValidator` para formato de data/hora.
- `filled`, `has_at`, `not_future`, `nat` (L55-80) — validadores de campo (string não-vazia, email com `@`, data não futura, inteiro ≥ 0).
- `Str`, `Day`, `Nat`, `Qty` (L73-84) — tipos Annotated reutilizáveis para os modelos.
- Modelos Pydantic (L87-140): `TutorIn, PetIn, VetIn, ProdutoIn, EntradaIn, AgendIn, CancelIn, UsoIn, AtendIn, ItemIn`.
- `hours(day)` (L250) — **regra de horário de funcionamento**: `{5: (8,12), 6: None}.get(weekday, (8,18))` → sáb 08-12, dom fechado, demais 08-18.
- `create_agend` (L254) — **todas as regras de criação de agendamento, nesta ordem exata** (ver seção Regras).
- `cancel_agend` (L296) — **regra de cancelamento/cancelamento tardio** (corte de 24h).
- `fatura(row)` / `item(...)` (L306-313) — deserializa `itens` JSON e calcula `total_centavos`; monta item de fatura.
- `create_atend` (L316) — **toda a lógica de atendimento**: validação de estoque, baixa de estoque, conclusão de agendamento, geração de fatura, tudo nesta função.
- Rotas: ver tabela em `SPEC.md`; cada rota é um `@app.<verbo>("/path")` isolado, 1:1 com uma linha da tabela do SPEC.

## Esquema do banco (SQLite, sem ORM, tipos dinâmicos — sem `NOT NULL`/FK declaradas, validação é 100% na camada Pydantic/handlers)
```
tutores(id PK, nome, email, telefone)
pets(id PK, nome, especie, tutor_id, data_nascimento)
veterinarios(id PK, nome, crmv UNIQUE)
produtos(id PK, nome, preco_centavos, estoque, estoque_minimo)
agendamentos(id PK, pet_id, veterinario_id, inicio, fim, duracao_minutos, status)
atendimentos(id PK, agendamento_id, anotacoes, produtos[JSON text], fatura_id)
faturas(id PK, tutor_id, atendimento_id, status, itens[JSON text])
```
- `agendamentos.inicio/fim`: string `"YYYY-MM-DDTHH:MM"`, comparáveis lexicograficamente (por isso funcionam em `WHERE inicio<? and fim>?` e `ORDER BY inicio`).
- `atendimentos.produtos` e `faturas.itens`: JSON serializado em coluna texto (`json.dumps`/`json.loads` manual nos handlers — não inferir estrutura pelo schema, ver `fatura()`/`read_atend_row()`).
- Sem foreign keys reais no SQLite: integridade referencial é garantida manualmente via `get(table, id)` antes de inserir/relacionar.

## Invariantes e regras de negócio (local exato)
1. **Moeda em centavos inteiros**, campo `*_centavos`; validado por `Nat` (main.py L83, StrictInt ≥0). Não aceitar float.
2. **Strings obrigatórias não-vazias/sem só espaço** → `filled()` (L55), usado em `Str` (L73) e `has_at` (L61).
3. **Email precisa conter `@`** → `has_at()` (L61), usado em `TutorIn.email` (L89).
4. **`crmv` único** → checado manualmente em `create_vet` (L213-217) antes do insert; 409 se já existir. (Não é constraint DB-level apesar do `unique` na coluna — tratar ali também se mudar o insert.)
5. **`data_nascimento` de pet não pode ser futura** → `not_future()` (L67), aplicado em `PetIn.data_nascimento` (L97).
6. **Delete de tutor bloqueado se tiver pets** → `delete_tutor` (L163-170), 409.
7. **Delete de pet bloqueado se tiver agendamentos** → `delete_pet` (L203-210), 409.
8. **Entrada de estoque**: `quantidade` deve ser `Qty` (> 0, L84); soma ao estoque existente em `entrada_produto` (L245-247).
9. **Criação de agendamento** (`create_agend`, L254-279), regras checadas NESTA ORDEM (a 1ª que falhar decide a resposta):
   - a. `pet_id`/`veterinario_id` existem → `get()` 404 (L256-257).
   - b. `duracao_minutos` múltiplo de 15, entre 15 e 120 → 422 (L259-260).
   - c. `inicio` > agora → 422 (L263-264).
   - d. Expediente: todo o intervalo `[inicio, fim]` no mesmo dia e dentro de `hours(dia)` → 422 (L265-269). Regra de horário centralizada em `hours()` (L250).
   - e. Conflito de agenda: nenhum outro agendamento do mesmo veterinário com status `agendado`/`concluido` sobrepondo `[inicio, fim)` semiaberto → 409 (L271-275); query usa `inicio<fim_novo and fim>inicio_novo`.
10. **Cancelamento de agendamento** (`cancel_agend`, L296-303): só `status=="agendado"` pode cancelar (senão 409); corte de **24h** entre `momento` (ou agora) e `inicio` define `status` final: `< 24h` → `"cancelado_tardio"`, senão `"cancelado"`. `momento` opcional no body para determinismo em testes.
11. **Atendimento** (`create_atend`, L316-345), ordem de verificação:
    - a. Agendamento existe (404), todo `produto_id` existe (404) — L318-319.
    - b. `agend.status == "agendado"`, senão 409 — L320-321.
    - c. Estoque suficiente para TODAS as quantidades agregadas por produto, senão 409 e **nada é alterado** — L322-327 (checagem acontece antes de qualquer `UPDATE`/`INSERT`).
    - d. Sucesso: agendamento → `"concluido"`; estoque decrementado por produto; fatura `"aberta"` criada com item fixo `"Consulta"` (`CONSULTA`=15000, L20) + um item por produto na ordem enviada, preço = preço do produto no momento (snapshot, não referência) — L328-343.
12. **Fatura**: `total_centavos` = soma dos itens, calculado dinamicamente em `fatura()` (L306-309), nunca persistido. `POST /faturas/{id}/itens` bloqueado se `status=="paga"` → 409 (L364-370). `POST /faturas/{id}/pagar` bloqueado se já paga → 409 (L373-377).
13. **Erros padrão**: 404 = recurso/id referenciado inexistente; 409 = conflito de estado; 422 = validação de formato/campo/regra. Corpo `{"detail": "..."}`. Ver `SPEC.md` L24-30.

## Convenções para código novo
- Manter tudo em `main.py` salvo decisão explícita de reestruturar (SPEC permite, mas aumenta custo de navegação — preferir não dividir sem necessidade).
- Reusar `get`/`insert`/`update` genéricos ao invés de SQL ad-hoc, exceto quando a regra exige lógica condicional (ex.: `create_agend`, `create_atend`).
- Novos campos monetários: sempre `*_centavos`, tipo `Nat`.
- Novas datas: `Day` (`YYYY-MM-DD`); novas datas+hora: `Annotated[str, parse(DT)]` (`YYYY-MM-DDTHH:MM`).
- Novas strings obrigatórias: tipo `Str` (não-vazia/sem só espaço).
- Toda nova rota de escrita que referencia outro recurso por id: validar com `get(table, id)` antes de qualquer mutação (padrão 404-antes-de-efeito já usado em todas as rotas).
- Regras de negócio que podem falhar em mais de uma condição: checar **na ordem exigida pelo SPEC.md** (a primeira falha define o código de erro) — replicar o padrão de `create_agend`/`create_atend`.
- Qualquer nova regra de negócio ou rota deve primeiro ser adicionada/validada contra `SPEC.md` (mesmo não podendo editá-lo, ele é o contrato — rodar a suíte de aceitação confirma conformidade).
- Listagens: sempre `ORDER BY id` salvo exceção documentada (agendamentos list é por `inicio, id`).

## Execução e testes
```bash
pip install -r requirements.txt
./run.sh                    # sobe API em :8000 (ou $PORT), banco vetclinic.db (ou $DB_PATH)
./test.sh                   # sobe servidor com DB temporário, roda toda a suíte, derruba servidor
./test.sh tests/acceptance  # roda só uma pasta/arquivo específico
```
- Testes falam com a API só via HTTP (`httpx`, fixture `api` em `conftest.py`), nunca importam `main.py` diretamente — rodar sempre via `./test.sh`, não via `pytest` direto (precisa do servidor no ar com `BASE_URL`).
