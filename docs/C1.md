# VetClinic API: guia para novos desenvolvedores

## 1. Visão geral

A VetClinic API é um serviço REST para gerir uma clínica veterinária. Ela cobre o ciclo completo de um atendimento:

1. Cadastrar **tutores** (donos), seus **pets**, os **veterinários** e os **produtos** de estoque, como vermífugos e rações.
2. **Agendar** uma consulta de um pet com um veterinário, respeitando expediente e conflitos de agenda.
3. **Cancelar** o agendamento. O cancelamento é classificado como normal ou tardio.
4. **Registrar o atendimento** realizado. Isso baixa o estoque, conclui o agendamento e gera uma **fatura** para o tutor.
5. **Complementar e pagar** a fatura.

A stack é Python 3.12, FastAPI, Pydantic e SQLite via o módulo `sqlite3` da biblioteca padrão. Não há ORM. As dependências estão fixadas em `requirements.txt`.

### O contrato é o `SPEC.md`

O arquivo `SPEC.md` é a fonte da verdade para rotas, campos, códigos de status e regras de negócio. A suíte em `tests/acceptance` verifica esse contrato. Em caso de dúvida sobre o comportamento esperado, leia a especificação antes do código.

Os arquivos abaixo são fixos e **não podem ser alterados**:

- `run.sh`
- `test.sh`
- `requirements.txt`
- `SPEC.md`
- `tests/acceptance/`

### Convenções do domínio

- **Dinheiro** é sempre inteiro em centavos, em campos `*_centavos`. Um valor como `10.5` é rejeitado com 422.
- **Datas** usam `YYYY-MM-DD`. **Data e hora** usam `YYYY-MM-DDTHH:MM`, em hora local, sem fuso e sem segundos.
- **IDs** são inteiros gerados pelo banco.
- **Listagens** vêm ordenadas por `id`. A exceção são os agendamentos, ordenados por `inicio`.
- **Erros** têm o formato `{"detail": "mensagem"}` e três códigos:

| Código | Significado | Exemplo |
| --- | --- | --- |
| 404 | Recurso inexistente, inclusive IDs citados no corpo | `tutor_id` que não existe ao criar um pet |
| 409 | O estado atual do sistema impede a operação | Excluir tutor que tem pets |
| 422 | Dado inválido | E-mail sem `@`, duração de 20 minutos |

## 2. Arquitetura

O código fica no pacote `vetclinic/`, organizado em camadas. Cada entidade tem um arquivo em cada camada, com o mesmo nome em português (`tutores.py`, `pets.py` e assim por diante).

```
main.py                      -> expõe `app` (uvicorn main:app)
vetclinic/
├── application.py           -> fábrica do FastAPI, registro de rotas e de erros
├── config.py                -> configuração (DB_PATH) e constantes compartilhadas
├── database.py              -> conexões SQLite, DDL do esquema, transações
├── errors.py                -> exceções de domínio (404/409/422)
├── validation.py            -> tipos Pydantic reutilizáveis (texto não vazio, datas, inteiros estritos)
├── routers/                 -> camada HTTP
├── schemas/                 -> modelos Pydantic de entrada e saída
├── services/                -> regras de negócio
└── repositories/            -> SQL
```

### Responsabilidade de cada camada

A regra de ouro é que **cada camada só conversa com a de baixo**: `routers → services → repositories`.

**`routers/`** traduz HTTP em chamadas de serviço. Cada função declara o `response_model`, o status de sucesso e a dependência de conexão, e delega ao serviço. Não há regra de negócio aqui. `routers/__init__.py` define `ConnectionDependency`, um atalho para `Depends(get_connection)`.

**`schemas/`** contém os modelos Pydantic. Os `*Input` validam o corpo da requisição e os `*Output` definem o formato da resposta. Normalmente `XOutput` herda de `XInput` e acrescenta `id`.

**`services/`** concentra as regras de negócio:

- Verificam existência e levantam `ResourceNotFoundError`.
- Verificam estado e levantam `StateConflictError`.
- Verificam regras de validação e levantam `InvalidDataError`.
- Abrem transações quando precisam de atomicidade.
- Cada serviço expõe um `get_<entidade>_or_raise`, reutilizado por outros serviços. Por exemplo, o serviço de agendamentos chama `get_pet_or_raise`.

**`repositories/`** é o único lugar com SQL. As funções recebem a conexão e valores simples e devolvem `dict` (alias `Row`) ou `None`, como em `find_*_by_id`. Elas **não** decidem regra nem levantam erros de domínio. Ficam fora delas todas as regras: existência, estado, estoque e conflito.

**`database.py`** reúne três coisas:

- `DATABASE_SCHEMA_STATEMENTS` com os `CREATE TABLE IF NOT EXISTS`.
- `get_connection`, uma dependência do FastAPI que abre uma conexão por requisição e a fecha no fim.
- O gerenciador de contexto `transaction`.

As conexões usam `isolation_level=None`, ou seja, o `sqlite3` não abre transações sozinho e cada transação é aberta explicitamente. Também ligam `PRAGMA foreign_keys = ON`. `transaction` usa `BEGIN IMMEDIATE`, que toma o lock de escrita logo no início. Assim uma verificação e a escrita que depende dela (conflito de agenda, estoque) não são intercaladas por outra requisição. Qualquer exceção dentro do bloco causa `ROLLBACK`.

**`errors.py`** define `DomainError` e três subclasses: `ResourceNotFoundError` (404), `StateConflictError` (409) e `InvalidDataError` (422). Em `application.py`, o dicionário `STATUS_CODE_BY_DOMAIN_ERROR` mapeia cada uma ao status HTTP, e um único handler monta o `{"detail": ...}`.

**`config.py`** lê `DB_PATH` a cada chamada de `load_settings()`. O padrão é `vetclinic.db`. Também guarda constantes compartilhadas: formatos de data, o preço fixo da consulta e o timeout do SQLite.

**`validation.py`** oferece tipos prontos para os schemas:

| Tipo | O que garante |
| --- | --- |
| `NonBlankText` | Texto não vazio e que não seja só espaços |
| `EmailText` | Texto não vazio que contém `@` |
| `DateText` | `YYYY-MM-DD` rígido (regex mais `strptime`) |
| `PastOrPresentDateText` | `DateText` que não pode ser futuro |
| `DateTimeText` | `YYYY-MM-DDTHH:MM` rígido |
| `StrictInteger`, `NonNegativeInteger`, `PositiveInteger` | Inteiros com `strict=True`, então `10.0` e `"10"` são rejeitados |

## 3. Como rodar e testar

### Preparação

```bash
python3.12 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### Subir a API

```bash
./run.sh                              # http://127.0.0.1:8000
PORT=9000 DB_PATH=/tmp/dev.db ./run.sh
```

O `run.sh` executa `uvicorn main:app`. As tabelas são criadas na inicialização (evento `lifespan` em `application.py`). Com a API no ar, a documentação interativa gerada pelo FastAPI fica em `http://127.0.0.1:8000/docs`.

### Rodar os testes

```bash
./test.sh                        # toda a suíte
./test.sh tests/acceptance       # uma pasta
./test.sh tests/acceptance/test_aceite_agendamentos.py
```

O `test.sh` cuida de tudo:

1. Sobe um servidor real com um banco temporário vazio, na porta `TEST_PORT` (padrão 8765).
2. Espera a porta abrir. Se o servidor não subir, mostra o `.server.log`.
3. Roda o `pytest` com `BASE_URL` apontando para esse servidor.
4. Derruba o servidor e apaga o banco ao final.

Os testes de aceitação são **caixa-preta**. Falam com a API só por HTTP (`httpx`) e não importam nada de `vetclinic`. As fixtures em `tests/acceptance/conftest.py` (`novo_tutor`, `novo_pet`, `novo_vet`, `novo_produto`, `agendar`) criam dados com valores únicos, então os testes não dependem da ordem de execução. Como não importam o código da aplicação, qualquer refatoração interna que preserve o contrato continua passando.

## 4. Fluxo de uma requisição típica

Vamos seguir `POST /agendamentos/{id}/atendimento`, que registra uma consulta realizada. É o caminho mais completo do sistema.

```http
POST /agendamentos/7/atendimento
{ "anotacoes": "Animal saudável", "produtos": [{"produto_id": 3, "quantidade": 2}] }
```

1. **Entrada.** O uvicorn entrega a requisição ao FastAPI. O Pydantic valida o corpo com `TreatmentInput` (`schemas/atendimentos.py`). Uma `quantidade` igual a 0 ou não inteira já falha aqui com 422.
2. **Conexão.** O FastAPI resolve `ConnectionDependency` chamando `get_connection`, que abre uma conexão SQLite exclusiva desta requisição.
3. **Rota.** `register_treatment` em `routers/agendamentos.py` chama `treatment_service.register_treatment(connection, 7, data)`.
4. **Serviço.** `services/atendimentos.py` abre uma `transaction` e, dentro dela, executa nesta ordem:
   - busca o agendamento (404 se não existir);
   - carrega os produtos (404 se algum não existir);
   - exige o status `agendado` (409 se não for);
   - confere o estoque, somando quantidades de um mesmo produto repetido na lista (409 se insuficiente);
   - baixa o estoque, marca o agendamento como `concluido` e insere o atendimento;
   - cria a fatura aberta para o tutor do pet, com o item "Consulta" e um item por produto.
5. **Repositórios.** Cada passo de persistência é uma função de `repositories/*.py` que executa SQL parametrizado.
6. **Commit ou rollback.** Se tudo passou, o `transaction` faz `COMMIT`. Se qualquer passo levantou exceção, faz `ROLLBACK`, e nada fica pela metade: nem estoque, nem status, nem fatura.
7. **Resposta.** O serviço monta o atendimento com o `fatura_id`. O FastAPI o filtra pelo `TreatmentOutput` e responde 201.
8. **Erros.** Se um `DomainError` foi levantado, o handler de `application.py` o converte em `{"detail": "..."}` com o status certo (404, 409 ou 422).
9. **Limpeza.** O `finally` de `get_connection` fecha a conexão.

## 5. Regras de negócio e onde estão implementadas

### 5.1 Cadastros

| Regra | Onde |
| --- | --- |
| Strings obrigatórias não podem ser vazias nem só espaços (422) | `validation.NonBlankText`, usado nos `schemas/` |
| E-mail do tutor deve conter `@` | `validation.EmailText`, usado em `schemas/tutores.py` |
| Espécie do pet: `cao`, `gato` ou `outro` | `Species` em `schemas/pets.py` |
| Data de nascimento do pet não pode ser futura (422) | `validation.PastOrPresentDateText` |
| `tutor_id` do pet deve existir (404) | `services/pets.py`, em `create_pet` e `replace_pet` |
| Tutor com pets não pode ser excluído (409) | `services/tutores.py`, em `delete_tutor` |
| Pet com agendamentos, em qualquer status, não pode ser excluído (409) | `services/pets.py`, em `delete_pet` |
| CRMV é único (409) | `services/veterinarios.py`, em `create_veterinarian`, mais `UNIQUE` em `database.py` |
| Valores monetários e de estoque são inteiros ≥ 0; a entrada de estoque exige `quantidade` > 0 | `schemas/produtos.py` |
| Entrada de estoque soma à quantidade existente | `services/produtos.py`, em `register_stock_entry` |

### 5.2 Agendamentos (`services/agendamentos.py`)

A função `create_appointment` aplica as regras **nesta ordem**, e a primeira que falhar define a resposta:

1. **Pet ou veterinário inexistente** → 404.
2. **Duração** múltiplo de 15, entre 15 e 120 minutos → senão 422. O padrão é 30 e está em `schemas/agendamentos.py`. A duração é validada no serviço, e não no schema, justamente para o 404 do passo 1 vir antes do 422.
3. **Início no futuro**, comparado com `datetime.now()` → senão 422.
4. **Expediente** → senão 422. O mapa `BUSINESS_HOURS_BY_WEEKDAY` define de segunda a sexta 08:00–18:00 e sábado 08:00–12:00. O domingo não aparece no mapa e portanto é fechado. O intervalo inteiro deve caber no mesmo dia. Uma consulta de 30 minutos às 17:30 numa terça é válida, e às 17:45 não é.
5. **Conflito de agenda** → 409. A verificação e o `INSERT` ocorrem na mesma transação. A consulta SQL está em `exists_overlapping_appointment` (`repositories/agendamentos.py`) e usa intervalos semiabertos `[inicio, fim)`, isto é, `inicio < novo_fim AND fim > novo_inicio`. Uma consulta que termina às 10:30 não conflita com outra que começa às 10:30. Só os status `agendado` e `concluido` bloqueiam o horário (`SLOT_BLOCKING_STATUSES`), então cancelamentos o liberam.

**Cancelamento** (`cancel_appointment`):

- Só agendamentos `agendado` podem ser cancelados (409 caso contrário).
- O corpo é opcional: `{"momento": "YYYY-MM-DDTHH:MM"}` define o instante do cancelamento. Sem ele, usa-se o horário atual. O campo existe para tornar os testes determinísticos.
- Faltando **24 horas ou mais** para o início, o status vira `cancelado`. Faltando menos, vira `cancelado_tardio`. Exatamente 24 horas conta como `cancelado`. A constante é `LATE_CANCELLATION_THRESHOLD`.

### 5.3 Atendimentos (`services/atendimentos.py`)

- A ordem das verificações é: agendamento inexistente (404), produto inexistente (404), agendamento que não está `agendado` (409), estoque insuficiente (409).
- Em caso de sucesso, **numa única transação**, o agendamento vai para `concluido`, o estoque de cada produto é reduzido e uma fatura `aberta` é criada para o tutor do pet.
- Se um mesmo produto aparece mais de uma vez na lista, as quantidades são somadas para validar o estoque (`_require_sufficient_stock`).
- Cada atendimento pertence a um único agendamento (`agendamento_id UNIQUE` em `database.py`).

### 5.4 Faturas (`services/faturas.py`)

- Itens de uma fatura de atendimento, nesta ordem:
  1. "Consulta", quantidade 1, 15000 centavos. O valor fica em `config.CONSULTATION_PRICE_IN_CENTS`.
  2. Um item por produto usado, na ordem enviada, com o **preço do produto no momento do atendimento**. Mudar o preço depois não altera faturas antigas.
- O **total não é armazenado**. `add_totals_to_invoice` calcula `total_centavos` de cada item (quantidade × valor unitário) e da fatura (soma dos itens) sempre que a fatura é lida.
- Só faturas `aberta` aceitam novos itens ou pagamento. Em fatura `paga`, as duas operações respondem 409 (`_require_invoice_open`).

## 6. Como adicionar uma nova entidade

Vamos usar como exemplo **Fornecedores**, um registro simples com `nome` (obrigatório) e `prazo_entrega_dias` (inteiro ≥ 0). Siga as camadas de baixo para cima e use `produtos` como modelo, por ser a entidade mais direta.

> A API é um contrato fechado pelo `SPEC.md`. Uma entidade nova só deve entrar depois de a especificação ser atualizada. Nesta base, `SPEC.md` e `tests/acceptance/` são arquivos protegidos: combine a mudança com a equipe antes de tocar neles.

### Passo 1: tabela (`database.py`)

Acrescente um `CREATE TABLE IF NOT EXISTS` à tupla `DATABASE_SCHEMA_STATEMENTS`:

```python
"""
CREATE TABLE IF NOT EXISTS fornecedores (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    nome TEXT NOT NULL,
    prazo_entrega_dias INTEGER NOT NULL
)
""",
```

Como é `IF NOT EXISTS`, bancos já existentes ganham a tabela na próxima subida. Alterar uma tabela existente **não** é coberto por esse mecanismo, pois não há migrações.

### Passo 2: schemas (`schemas/fornecedores.py`)

```python
"""Schemas de fornecedores."""

from pydantic import BaseModel

from vetclinic.validation import NonBlankText, NonNegativeInteger


class SupplierInput(BaseModel):
    """Corpo de criação de um fornecedor."""

    nome: NonBlankText
    prazo_entrega_dias: NonNegativeInteger


class SupplierOutput(SupplierInput):
    """Fornecedor retornado pela API."""

    id: int
```

Use os tipos de `validation.py` em vez de `str` ou `int` soltos. É isso que garante o 422 para texto em branco e para números não inteiros.

### Passo 3: repositório (`repositories/fornecedores.py`)

Só SQL, sem regra de negócio:

```python
"""Persistência de fornecedores."""

import sqlite3

from vetclinic.repositories import Row, row_to_dict


def insert_supplier(connection: sqlite3.Connection, nome: str, prazo_entrega_dias: int) -> int:
    """Insere um fornecedor e devolve o id gerado."""
    cursor = connection.execute(
        "INSERT INTO fornecedores (nome, prazo_entrega_dias) VALUES (?, ?)", (nome, prazo_entrega_dias)
    )
    return int(cursor.lastrowid)


def find_supplier_by_id(connection: sqlite3.Connection, supplier_id: int) -> Row | None:
    """Busca um fornecedor pelo id."""
    return row_to_dict(
        connection.execute("SELECT * FROM fornecedores WHERE id = ?", (supplier_id,)).fetchone()
    )


def list_suppliers(connection: sqlite3.Connection) -> list[Row]:
    """Lista todos os fornecedores por id crescente."""
    return [dict(row) for row in connection.execute("SELECT * FROM fornecedores ORDER BY id")]
```

Use sempre parâmetros `?`, nunca interpolação de valores do usuário no SQL.

### Passo 4: serviço (`services/fornecedores.py`)

Aqui ficam as regras. Exponha um `get_supplier_or_raise` para que outros serviços possam reutilizá-lo.

```python
"""Regras de negócio de fornecedores."""

import sqlite3

from vetclinic.errors import ResourceNotFoundError
from vetclinic.repositories import Row
from vetclinic.repositories import fornecedores as supplier_repository
from vetclinic.schemas.fornecedores import SupplierInput

SUPPLIER_NOT_FOUND_MESSAGE = "Fornecedor não encontrado"


def get_supplier_or_raise(connection: sqlite3.Connection, supplier_id: int) -> Row:
    """Devolve o fornecedor ou levanta `ResourceNotFoundError`."""
    supplier = supplier_repository.find_supplier_by_id(connection, supplier_id)
    if supplier is None:
        raise ResourceNotFoundError(SUPPLIER_NOT_FOUND_MESSAGE)
    return supplier


def create_supplier(connection: sqlite3.Connection, data: SupplierInput) -> Row:
    """Cadastra um fornecedor."""
    supplier_id = supplier_repository.insert_supplier(connection, data.nome, data.prazo_entrega_dias)
    return get_supplier_or_raise(connection, supplier_id)


def list_suppliers(connection: sqlite3.Connection) -> list[Row]:
    """Lista os fornecedores."""
    return supplier_repository.list_suppliers(connection)
```

Duas regras práticas para o serviço:

- **Verificação seguida de escrita** que não pode ser intercalada por outra requisição (conflito, unicidade, estoque) precisa estar dentro de `with transaction(connection):`.
- Quando mais de uma regra puder falhar, respeite a ordem da especificação. Por exemplo, os 404 vêm antes dos 409.

### Passo 5: rotas (`routers/fornecedores.py`)

```python
"""Rotas de fornecedores."""

from fastapi import APIRouter, status

from vetclinic.routers import ConnectionDependency
from vetclinic.schemas.fornecedores import SupplierInput, SupplierOutput
from vetclinic.services import fornecedores as supplier_service

router = APIRouter(prefix="/fornecedores", tags=["fornecedores"])


@router.post("", response_model=SupplierOutput, status_code=status.HTTP_201_CREATED)
def create_supplier(data: SupplierInput, connection: ConnectionDependency):
    """Cadastra um fornecedor."""
    return supplier_service.create_supplier(connection, data)


@router.get("", response_model=list[SupplierOutput])
def list_suppliers(connection: ConnectionDependency):
    """Lista os fornecedores."""
    return supplier_service.list_suppliers(connection)


@router.get("/{supplier_id}", response_model=SupplierOutput)
def get_supplier(supplier_id: int, connection: ConnectionDependency):
    """Consulta um fornecedor."""
    return supplier_service.get_supplier_or_raise(connection, supplier_id)
```

Para um `DELETE` com 204, siga `routers/pets.py`: o endpoint devolve `Response(status_code=status.HTTP_204_NO_CONTENT)`.

### Passo 6: registrar o router (`application.py`)

Importe o módulo e acrescente-o à tupla `ROUTER_MODULES`:

```python
from vetclinic.routers import (
    agendamentos, atendimentos, faturas, fornecedores, pets, produtos, tutores, veterinarios,
)

ROUTER_MODULES = (tutores, pets, veterinarios, produtos, agendamentos, atendimentos, faturas, fornecedores)
```

Sem esse passo, as rotas existem no código mas **não** aparecem na API.

### Passo 7: testar

Se precisar de testes novos, crie-os em `tests/`, fora de `tests/acceptance/` (que é protegida), chamando a API só por HTTP. Depois rode `./test.sh`.

### Armadilhas comuns

- **Nova exceção de domínio.** O handler escolhe o status pelo **tipo exato** do erro (`STATUS_CODE_BY_DOMAIN_ERROR[type(error)]`). Uma subclasse nova de `DomainError` precisa ser registrada nesse dicionário. Prefira reutilizar as três existentes.
- **Ordem das regras.** Se a especificação define uma ordem de verificação, o código precisa respeitá-la. Foi por isso que a duração do agendamento é validada no serviço e não no schema.
- **Valores monetários.** Use `NonNegativeInteger` ou `PositiveInteger`, com `strict=True`, para que `10.5` e `"10"` virem 422.
- **Regras no lugar errado.** Mantenha o SQL nos repositórios e as regras nos serviços. As rotas só delegam.
